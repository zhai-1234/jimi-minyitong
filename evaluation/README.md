# 基米民易通 RAG 评测体系

用于量化「社会救助政策问答」智能体的回答质量，并在改动工作流（检索策略、提示词、分段粒度等）后验证效果是否真的提升。仅依赖 Python 标准库，无需安装第三方包。

## 目录结构

```
evaluation/
├── dataset/questions.jsonl   # 50 条标注测试题（JSONL，一行一题）
├── mock/responses.json       # 演示模式用的模拟回答（仅覆盖部分题目）
├── run_eval.py               # 评测主脚本：调用 Dify、计算指标、生成报告
├── compare_reports.py        # 对比两次评测结果（基线 vs 优化后）
└── results/<label>/          # 输出：results.csv、summary.json、report.md
```

## 测试集

共 50 题，覆盖 6 类场景：

| 类别 | 题数 | 考察点 |
| --- | --- | --- |
| `single_policy` 单政策查询 | 15 | 低保、特困、临时救助等单一政策的条件、材料、流程 |
| `multi_policy` 多政策交叉 | 8 | 同一诉求涉及多项政策时的覆盖与衔接 |
| `colloquial` 口语化表述 | 8 | 口语提问（"低保咋弄啊"）下的意图理解 |
| `cantonese` 粤语问法 | 6 | 粤语书面表达与地方习惯用语 |
| `out_of_scope` 超纲/闲聊 | 7 | 非社会救助问题应正确拒答并引导 |
| `edge_case` 边界情形 | 6 | 标准查询、政策互斥、投诉渠道等易错点 |

每题的标注字段：

```json
{
  "id": "sp-01",
  "category": "single_policy",
  "question": "申请最低生活保障（低保）需要满足哪些条件？",
  "expected_keywords": [["共同生活", "家庭成员"], ["人均收入", "收入低于"], ["财产"]],
  "expected_sources": ["最低生活保障"],
  "should_refuse": false
}
```

- `expected_keywords`：要点分组，**组内任一同义词命中即算该组命中**，用于计算要点召回。
- `expected_sources`：回答应引用的政策文档名片段（匹配检索结果的 `document_name`）。
- `should_refuse`：超纲题标记，答案中出现拒答/引导标志词（"无法""建议咨询民政部门""12345"等）即算正确。

> 标注由通用政策口径整理，落地前应请业务人员按本地文件校准关键词与要点；政策更新后需同步更新测试集。

> 2026-11-12 首次真实评测后，对 6 道题补充了同义表述（如「最低生活保障标准」计入「低保标准」、「救助站」计入「救助管理站」、「残疾/因病致贫」等），避免因用词差异误判。调整前的严格词表结果保留在 `results/baseline-v1-strict/`。

## 指标

| 指标 | 计算方式 | 说明 |
| --- | --- | --- |
| 关键要点召回率 | 命中要点组数 / 标注要点组数，再对题目取平均 | 衡量回答是否答全 |
| 来源命中率 | 至少命中一个应引用文档的题目占比 | 衡量检索是否找对文件；接口未回传引用时显示为 `-` |
| 来源覆盖率 | 命中应引用文档数 / 标注文档数，再取平均 | 衡量多文档覆盖 |
| 来源提及率（代理） | 答案文本中出现应引用文档名的题目占比 | 检索节点位于迭代子图内时 Dify 不回传 `retriever_resources`，用此代理指标补充观察 |
| 拒答正确率 | 超纲题正确拒答的占比 | 衡量边界控制 |
| 平均 / P95 延迟 | 单题接口耗时 | 衡量体验 |
| 平均 token | Dify 返回的 usage.total_tokens | 衡量成本 |

50 题全部完成、0 调用失败：

| 指标 | 数值 |
| --- | --- |
| 关键要点召回率 | 93.4%（43 道有要点题中 35 题满分） |
| 来源命中率 | 不可用（见下方排查记录） |
| 来源提及率（代理） | 86.1% |
| 拒答正确率 | 100%（7 道超纲题全部正确拒答/引导） |
| 平均延迟 / P95 | 8.8 s / 16.2 s |
| token 用量 | 不可用（工作流未上报 usage） |

分类表现：单政策 93.3%、多政策交叉 91.7%、口语化 95.8%、粤语 94.4%、边界情形 91.7%、超纲 100%。

主要能力缺口（来自失败样例）：

- 残疾人家庭的就业救助、康复服务未覆盖（mp-06）
- 脱贫不稳定户帮扶未提及临时救助（mp-08）

## 延迟优化结果（2026-11-12）

**改动内容**

1. **重写「问题分析」提示词**：删除原提示词中引号错乱的示例，固定输出 3 个短检索词（`max_tokens=80`、`temperature=0.1`），耗时从约 3.4 s 降至约 1.7 s。
2. **「迭代 2」改为并行**：4 个子问题的知识检索并行执行，迭代总耗时从约 4.2 s 降至约 2.3 s。
3. **精简回答提示词**：保留「知识库优先、标明出处、同语言回复、超纲拒答」等约束，要求 350 字以内、结构化输出；平均答案长度从 932 字降至 376 字，回答生成耗时从约 4.5 s 降至约 2.1 s。
4. **修复子问题切分逻辑**：原代码只按英文逗号切分，而模型实际输出中文引号，导致「多子问题检索」退化为单条检索；改为兼容中英文标点、去重并限制最多 4 条。

**对比结果**（同一 50 题测试集，逐一严格复测）

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 平均延迟 | 8813 ms | 7782 ms | **-11.7%** |
| P50 延迟 | 7990 ms | 7082 ms | -11.4% |
| P95 延迟 | 16184 ms | 12883 ms | **-20.4%** |
| 关键要点召回率 | 93.4% | 93.8% | +0.4 pt |
| 拒答正确率 | 100% | 100% | 持平 |
| 平均答案长度 | 932 字 | 376 字 | -59.6% |
| 来源提及率（代理） | 86.1% | 76.7% | -9.4 pt |

**取舍说明**：答案变短后引用政策文件名的机会减少，来源提及率代理指标下降；多政策交叉类召回率由 91.7% 降至 83.3%，但总体召回率小幅上升。优化前的提示词与工作流快照保存在 `diagnostics/workflow-before-latency-opt.json`，对比报告见 `results/comparison.md`。

## 引用来源修复（2026-11-12）

**根因**（阅读 Dify 1.9.1 源码确认，两层原因叠加）：

1. `EventManager.dispatch()` 对迭代/循环内产生的事件只收集、不转发（"Events in loops or iterations are always collected"），因此检索节点放在「迭代 2」里时，引用事件永远到不了 API。
2. 引用来源由 **LLM 节点根据上下文变量自动生成**：上下文必须是检索结果数组（元素含 `metadata._source == "knowledge"`）；此前 LLM 的上下文接的是「字符串转换」节点，输出为纯字符串，只会生成空引用。

**修复方式**

- 把「知识检索」移出迭代，迭代节点删除；「问题分析」→「数组」代码节点同时输出 `result`（数组）和 `query`（子问题用「；」拼接的融合查询）。
- LLM 上下文直接指向知识检索的 `result` 数组，Dify 据此生成引用来源。
- 知识库检索 top_k 由 2 调整为 4，提高多政策问题的文档覆盖。

**最终对比**（同一 50 题测试集）

| 指标 | 优化前（基线） | 延迟优化后 | 引用修复后 |
| --- | --- | --- | --- |
| 关键要点召回率 | 93.4% | 93.8% | **94.2%** |
| 来源命中率 | 不可用 | 不可用 | **72.1%** |
| 来源覆盖率 | 不可用 | 不可用 | 69.8% |
| 拒答正确率 | 100% | 100% | **100%** |
| 平均延迟 | 8813 ms | 7782 ms | **6153 ms**（-30.2%） |
| P95 延迟 | 16184 ms | 12883 ms | **9351 ms**（-42.2%） |
| 调用失败数 | 0 | 0 | 0 |

**架构说明**：修复后工作流不再使用迭代节点做知识检索（Dify 的限制下无法同时保留迭代与引用回传），改为「查询拆解 → 融合查询单次检索 → 生成回答」。若需保留多查询并行检索，需要把检索拆成多个静态并行分支（固定查询数），属于后续可选项。

**前端联调**：同时修复了前端 SSE 解析缺陷——Dify 新版将事件名放在 `data.event` 字段而非 `event:` 行，导致 `message_end` 从未被识别、来源面板永远为空；修复后前端可正常展示引用政策来源。优化前的工作流快照见 `diagnostics/workflow-before-citation-fix.json`。

## 来源命中优化（2026-11-12）

引用修复后来源命中率仅 72.1%，逐题分析发现三类问题并逐一处理：

1. **标注指向不存在的文档**：知识库没有独立的医疗/教育/住房/就业救助文件，相关条款实际在《南海区分层分类社会救助帮扶惠民清单（2025）》（文档内含医疗救助 19 段、教育救助 4 段、住房救助 2 段、就业救助 2 段）。修正 9 道题的 `expected_sources`。
2. **融合查询语义稀释**：把 4 个子问题拼成一条长查询后，向量相似度被摊薄，反而召回不到目标文档。在 17 题平衡子集上做了 A/B 实验：

| 配置 | 来源命中率 | 平均延迟 |
| --- | --- | --- |
| 融合查询（4 子问题），top_k=4 | 70.6% | 7.8 s |
| 融合查询，top_k=8 | 76.5% | 7.2 s |
| 融合查询，纯向量，top_k=8 | 76.5% | 8.9 s |
| **原始问题检索，top_k=8** | **82.3%** | 6.6 s |
| 原始问题 + 子问题拼接，top_k=8 | 70.6% | 6.4 s |
| 原始问题，top_k=4 | **82.3%** | 6.1 s |

3. **超大文档霸榜**：18.7 万字的《广东省流浪救助管理工作质量手册》分段极多，在其他主题查询中挤占 top_k 名额；实验性停用后子集指标无显著变化，已恢复启用（该文档对流浪救助问题仍需保留）。

**最终方案**：普通提问直接用用户原始问题检索；用户上传文件时仍用「原问题 + 子问题」融合查询（保留文件问答能力）。检索方式 hybrid，top_k 统一为 4。

**全量 50 题结果**（对比引用修复后）：

| 指标 | 引用修复后 | 来源优化后 | 变化 |
| --- | --- | --- | --- |
| 来源命中率 | 72.1% | **90.7%** | **+18.6 pt** |
| 来源覆盖率 | 69.8% | 84.1% | +14.3 pt |
| 关键要点召回率 | 94.2% | 92.2% | -1.9 pt |
| 拒答正确率 | 100% | 100% | 持平 |
| 平均延迟 | 6153 ms | 6237 ms | +1.4% |
| P95 延迟 | 9351 ms | **7217 ms** | **-22.8%** |

**取舍说明**：短查询的检索更聚焦、引用更准，但覆盖多政策交叉问题的广度略降（召回率 -1.9 pt）；P95 反而显著下降。调优过程数据保留在 `results/tuning/`，对比报告见 `results/comparison-source.md`。

## 嵌入模型升级实验（2026-11-13）

把知识库嵌入模型从 tongyi `text-embedding-v1` 升级到 `text-embedding-v4`（1024 维），并重建全部索引。

**重建过程中发现 Dify 1.9.1 的一个缺陷**：`deal_dataset_vector_index_task` 在清理索引后访问已脱离会话的文档对象，抛出 `DetachedInstanceError`，导致重建失败、文档卡在 indexing。已在 API 与 worker 容器内打最小补丁（先取出文档 id/doc_form 再清理），原文件备份在 `diagnostics/deal_dataset_vector_index_task.py.orig`。补丁仅存在容器内，重建容器后会丢失。

**效果（全量 50 题）**：

| 指标 | v1（来源优化后） | v4 升级后 |
| --- | --- | --- |
| 关键要点召回率 | 92.2% | **95.7%** |
| 来源命中率 | 90.7% | 76.7% |
| 拒答正确率 | 100% | 100% |
| 平均延迟 | 6237 ms | **5951 ms** |

结论：v4 提升了回答完整度与速度，但文档级来源命中下降。逐题分析发现根因不在嵌入模型本身：

- 知识库关键词检索（BM25）对中文返回空，所谓 hybrid 实际只有向量检索；
- 教育/住房/就业/医疗救助条款只存在于《惠民清单》xls 中，解析后的分段充斥着 `Unnamed` 列名噪声，向量相似度低，检索不中；
- 18.7 万字的《流浪救助管理质量手册》分段多，在无关问题中挤占 top_k。

**下一步方案**：把惠民清单中医疗/教育/住房/就业/残疾人救助整理成 5 份干净归纳文档（已生成于 `kb-fixes/`），补入知识库后重新评测。文档上传需要“知识库 API”密钥（应用 API 密钥无知识库写权限）。

**知识库补文档后的实验矩阵**（同一 50 题）：

| 配置 | 要点召回率 | 来源命中率 | 平均延迟 |
| --- | --- | --- | --- |
| v1 嵌入（历史最佳） | 92.2% | 90.7% | 6237 ms |
| v4，未补文档 | 95.7% | 76.7% | 5951 ms |
| v4 + 5 份归纳文档（重排取向量 Top4） | 95.3% | 83.7% | 6332 ms |
| v4 + 文档（重排：文档名 Top4） | 90.7% | 86.1% | 6600 ms |
| v4 + 文档（重排：文档名 Top3 + 向量 Top3） | 87.6% | 88.4% | 6827 ms |
| **v1 + 5 份归纳文档（停用就业文档后）** | **94.6%** | **90.7%** | 6427 ms |
| **v1 + 归纳文档 + 办理指南（最终配置）** | **95.3%** | **97.7%** | 6600 ms |

结论：补文档把 v4 的来源命中从 76.7% 提升到 83.7-88.4%；给重排加入“文档名优先”后，教育/住房/临时救助等题能命中正确文件，但候选集中又牺牲了回答覆盖面（召回下降）。切回 v1 并保留新文档后，来源命中共 90.7%（与无文档时持平），住房救助题由未命中变为命中，但个别题（如“家里突然出事”）被新文档干扰而丢失来源。

**最终配置（v1 + 归纳文档）**：召回 94.6%、来源命中 90.7%、拒答 100%、平均延迟 6.43 s、P95 约 9 s。其中「就业救助（惠民清单归纳）.txt」已停用并删除向量——惠民清单中没有职业培训/公益性岗位内容，该文档使就业题回答变窄（召回下降），停用后恢复。

**仍存在的 4 道来源未命中题**：被拒申诉（cl-06）、“家里突然出事”（cl-03）、上门办理（yue-04）、去哪里办理（edge-04），均为办理渠道/申诉类问题，现有政策文档中没有直接对应章节，后续可补充一份“办理渠道与咨询投诉指南”文档解决。

**办理指南补充（最终）**：新增《办理指南（最低生活保障·特困·临时救助；镇街受理与咨询投诉）》，内容取自各流程原文与镇街联系方式，包含申请渠道、三类救助流程时限、材料一次性补正、异议复核与12345投诉渠道、各镇街联系电话。补入后来源命中 90.7% → **97.7%**，召回率保持 **95.3%**，P95 延迟 8.4 s。唯一未命中的 edge-05 实际检索到了办理指南（材料补正章节），属于标注仍指向旧文档的名称差异。

> 评测存在单题波动：同一配置重复运行时，要点召回率会有 ±1-2 题（约 ±2-4 个百分点）的差异，对比时应同时看多次结果与来源命中这类相对确定的指标。

## 工作流导出（beta1.3.0）

当前工作流已用 Dify 官方导出服务生成 `基米民易通beta1.3.0.yml`（`dify/` 目录），共 9 个节点：开始 → 迭代（文件提取）→ 问题分析 → 数组 → 知识检索 → LLM → 直接回复。

导入到其他 Dify 实例时需要注意：

1. 安装并配置插件：`deepseek`（问答模型必需）、`wenxin`（仅被知识检索节点的重排配置引用，当前重排已关闭，可不配置）；
2. DSL **不包含知识库**：需要预先创建知识库并上传原政策文档及 `kb-fixes/` 下的 6 份归纳文档；
3. 知识库嵌入模型选择 `text-embedding-v1`（当前评测最优），检索方式 hybrid、top_k=4；
4. 导入后打开「知识检索」节点，重新选择本实例的知识库（原 DSL 中记录的是导出实例的数据集 ID）。

## 使用

演示模式（不调用 Dify，用 `mock/responses.json` 的模拟回答验证脚本链路）：

```bash
python run_eval.py --mode mock --label demo
```

真实评测：

```bash
set DIFY_API_KEY=app-xxxxxxxx          # Windows cmd；PowerShell 用 $env:DIFY_API_KEY="app-xxx"
set DIFY_API_BASE=http://your-dify-host/v1
python run_eval.py --mode real --label baseline
```

可选参数：`--limit N` 只跑前 N 题、`--workers N` 并发（注意 Dify 限流）、`--timeout 秒`、`--dataset` 指定其他测试集。

输出到 `results/<label>/`：

- `results.csv`：每题得分、延迟、token、检索来源、完整回答（可用 Excel 打开）
- `summary.json`：各指标汇总与分类统计
- `report.md`：可直接放进项目文档的评测报告（含失败样例清单）

## 基线 vs 优化后对比

同一测试集上，分别用改动前后的工作流各跑一次，再对比：

```bash
python compare_reports.py results/baseline/summary.json results/improved/summary.json \
    --baseline-name 单轮检索 --improved-name 迭代检索 --out results/comparison.md
```

推荐对比实验：

1. 单轮检索 vs 迭代式多子问题检索（当前工作流的核心设计）
2. 关闭/开启 rerank（gte-rerank）
3. 知识库分段粒度（如 512 vs 1024 字符、重叠比例）
4. 不同 top_k（2 / 4 / 6）
5. 提示词迭代前后（如增加"引用政策出处"约束）

## 局限与后续改进

- 关键词匹配是**确定性代理指标**，不理解语义；适合做回归对比，不宜当作绝对正确率。
- 可扩展 **LLM-as-judge**：用另一个模型按评分标准给答案打 1~5 分，与本脚本的规则分数交叉验证。
- 失败样例（`report.md` 中的待改进清单）可直接沉淀为新测试题或知识库补充条目，形成"评测 → 修复 → 回归"闭环。

## 排查记录：检索为空问题（2026-11-12）

首次真实评测时发现所有回答都提示"参考内容为空"，逐层排查后定位到两个叠加问题：

1. **重排模型静默失败**：知识库与检索节点配置的重排模型为 tongyi `gte-rerank`，直接调用返回 0 条结果（`gte-rerank-v2` 同样为空）；换用 wenxin `bce-reranker-base` 后短文本正常，但处理知识库长分块时百度 API 返回 400。最终关闭重排，使用向量检索结果作为基线。
2. **引用来源不回传**：知识检索节点位于迭代子图内时，Dify 不会向上层传播 `retriever_resources`（日志可见 `Unhandled event type: NodeRunRetrieverResourceEvent`），因此接口与历史消息里的引用均为空，评测中的来源指标改用答案文本代理。
3. 另外发现系统级"对话命名"模型配置了不存在的 `qvq-max`，会话命名生成报 404（不影响问答主链路）。

修复前的工作流快照保存在 `diagnostics/workflow-backup-published.json`。

> 后续可选优化：把知识检索移出迭代（或增加专门的来源汇总节点），即可恢复引用回传与真实的来源命中率指标；重排可改用支持长文本的服务商。
