# 项目知识文档：基米民易通

> 用来快速理解项目原理、复现实验与准备面试。简历条目见 [简历-基米民易通.md](简历-基米民易通.md)，运行方式见根目录 [README](../README.md)。

## 1. 项目要解决什么

社会救助政策分散在省市文件、区级惠民清单和镇街办事指南中，群众提问往往口语化甚至使用粤语。项目目标是做一个能答准「条件、材料、流程、渠道」的问答智能体，并且**必须能指出依据哪份文件**，避免模型编造。

系统由四部分组成：

1. Dify 工作流 + 知识库（智能体本体）；
2. Vue 3 前端（对话、来源、朗读、语音、上传）；
3. Python 评测体系（50 题、六类场景）；
4. 可选 Spring Boot 日志服务（落库与查询）。

## 2. 总体架构

```
浏览器
  │ SSE / HTTP
  ▼
frontend/（Vue 3 + Pinia）
  │ 开发：Vite 代理 /v1 → http://localhost
  │ 生产：Nginx 反代 /v1（关闭 proxy_buffering）
  ▼
Dify 1.9.1
  ├─ advanced-chat 工作流（9 节点）
  ├─ 知识库 dataset 452cebfd…（25 份原始文档 + 6 份归纳文档 + 1 份办理指南）
  ├─ 模型：deepseek-chat（问答/问题分析）、text-embedding-v1、paraformer-realtime-v2（STT）、tts-1
  └─ PostgreSQL / Redis / Weaviate / 插件守护进程
```

## 3. 工作流（9 个节点）

```
开始
 └→ 迭代（文件提取，仅用户上传文件时生效）
     └→ 问题分析（LLM：输出 3 个短检索词，max_tokens=80，temperature=0.1）
         └→ 数组（Code：输出 result 数组与 query）
             └→ 知识检索（hybrid，top_k=4）
                 └→ LLM(1)（回答 ≤350 字，上下文直接绑定检索结果数组）
                     └→ 直接回复
```

关键点：

- **知识检索必须在迭代节点之外**。Dify `EventManager.dispatch()` 对迭代/循环内的事件只收集、不转发，放在迭代里时 `retriever_resources` 永远到不了 API。
- **LLM 的上下文要直接接检索结果数组**（元素含 `metadata._source == "knowledge"`），Dify 才会生成引用；接字符串节点只会得到空引用。
- 普通提问直接用**用户原始问题**检索；带文件时用「原问题 + 子问题」融合查询，保留文件问答能力。

## 4. 知识库与检索

- 原始文档：低保、特困、临时救助、流浪救助、惠民清单、粤府/粤民规文件等。
- 补充文档（`evaluation/kb-fixes/`）：医疗、教育、住房、就业、残疾人救助 5 份归纳文档 + 办理指南；「就业救助（惠民清单归纳）」因内容缺失已停用并删除向量。
- 嵌入：`text-embedding-v1`（最终选择）；检索方式 hybrid，top_k=4。
- 中文 BM25 实际返回空，hybrid 主要由向量检索贡献；检索质量提升靠文档治理与查询策略，而不是关键词召回。

## 5. 评测体系

### 5.1 数据集

50 题、6 类：单政策 15、多政策交叉 8、口语化 8、粤语 6、超纲/闲聊 7、边界 6。

每题字段：

```json
{
  "id": "sp-01",
  "category": "single_policy",
  "question": "申请最低生活保障（低保）需要满足哪些条件？",
  "expected_keywords": [["共同生活", "家庭成员"], ["人均收入", "收入低于"], ["财产"]],
  "expected_sources": ["最低生活保障"],
  "should_refuse": false
}
```

### 5.2 指标

| 指标 | 定义 |
| --- | --- |
| 关键要点召回率 | 每题命中要点组数 / 标注组数，再对题目平均；组内任一同义词命中即算命中 |
| 来源命中率 | 至少命中一个应引用文档的题目占比 |
| 来源覆盖率 | 命中应引用文档数 / 标注文档数，再平均 |
| 来源提及率（代理） | 答案文本出现文档名的题目占比（引用接口不可用时使用） |
| 拒答正确率 | 超纲题出现拒答/引导标志词的比例 |
| 延迟 | 单题接口耗时，报告平均与 P95 |
| token | Dify usage.total_tokens |

局限：关键词匹配是确定性代理，不理解语义，适合回归对比；单次运行要点召回有 ±2~4 个百分点波动，应看多次结果与来源命中这类更稳定的指标。

### 5.3 使用

```bash
python run_eval.py --mode mock --label demo        # 不调用 Dify
set DIFY_API_KEY=... & set DIFY_API_BASE=http://.../v1
python run_eval.py --mode real --label baseline
python compare_reports.py results/a/summary.json results/b/summary.json --out results/comparison.md
```

输出：`results/<label>/results.csv`（逐题）、`summary.json`、`report.md`。

## 6. 关键问题排查记录

### 6.1 引用来源为空（最重要）

两层根因叠加：

1. 知识检索位于迭代子图内，Dify 不向上转发 `NodeRunRetrieverResourceEvent`；
2. LLM 上下文接的是「字符串转换」节点，Dify 无法据此生成引用。

修复：把检索移出迭代，改为「查询拆解 → 单次融合检索」；LLM 上下文直接接检索 `result` 数组；top_k 从 2 调到 4。修复后来源命中从不可用变为 **72.1%**。

### 6.2 延迟优化（-30.2%）

- 重写问题分析提示词：修复引号错乱的示例，固定输出 3 个短检索词，耗时 3.4 s → 1.7 s；
- 回答提示词要求 350 字以内、结构化，生成 4.5 s → 2.1 s，答案长度 932 → 376 字；
- 「迭代 2」改为并行（后来整体移出迭代）；
- 修复子问题切分：原代码只按英文逗号切，模型输出中文引号导致退化为单条检索。

平均延迟 8813 ms → 6153 ms（-30.2%），P95 16184 ms → 9351 ms。

### 6.3 来源命中优化（72.1% → 90.7% → 97.7%）

- 标注修正：医疗/教育/住房/就业条款实际在《惠民清单》，不是独立文档，修正 9 道题的 `expected_sources`；
- 查询策略 A/B（17 题平衡子集）：融合查询 top4 70.6%、top8 76.5%、原始问题 top8 **82.3%**、原始问题 top4 **82.3%**；最终普通提问用原始问题检索；
- 超大文档《广东省流浪救助管理工作质量手册》分段过多，曾在无关问题中挤占 top_k；停用实验无显著收益，已恢复；
- 补充 6 份归纳文档与办理指南后，来源命中 **97.7%**、要点召回 **95.3%**。

### 6.4 嵌入模型实验（v1 vs v4）

升级 `text-embedding-v4`（1024 维）并重建索引：要点召回 92.2% → **95.7%**，但来源命中 90.7% → 76.7%。根因是惠民清单解析噪声与长文档挤占，不是嵌入本身。最终保留 v1 + 归纳文档 + 办理指南的组合。

### 6.5 重建索引 DetachedInstanceError

Dify 1.9.1 的 `deal_dataset_vector_index_task` 先批量更新文档状态，再遍历原 ORM 对象读取 `id/doc_form`；批量更新使对象过期，访问时抛 `DetachedInstanceError`，文档卡在 indexing。

补丁：批量更新前先快照 `(id, doc_form)`，循环只用快照。仓库已把补丁脚本化：

- `dify/patches/deal_dataset_vector_index_task.py`（带 `# [jimi-patch]` 标记）
- `apply-index-patch.sh` / `.ps1`（幂等，支持 check/restart）
- `docker-compose.patch.yml`（推荐，挂载后容器重建不丢）

### 6.6 中文 BM25 与重排

- hybrid 里的关键词检索对中文返回空，指标与纯向量基本一致；
- tongyi `gte-rerank`（及 v2）返回 0 条，wenxin `bce-reranker-base` 对长分块返回 400，最终关闭重排；
- 做过多组「重排取向量 TopN / 文档名优先」实验，收益不稳定且牺牲覆盖面，未启用。

### 6.7 SSE 解析

Dify 新版把事件名放在 `data.event` 而非 `event:` 行，旧解析导致 `message_end` 永远识别不到、来源面板为空。前端已兼容两者；Nginx 必须 `proxy_buffering off` 否则流式不增量。

### 6.8 平台默认模型坑

`tenant_default_models` 里 text-generation 被配成不存在的 `qvq-max`，导致会话命名与「建议问题」静默失败（日志 404）；已改为 `deepseek-chat`。speech2text 原为 `paraformer-realtime-v1`，对上传音频返回空文本，切换 `paraformer-realtime-v2` 后正常。

### 6.9 前端响应式 bug

附件对象在 push 进响应式数组后被直接修改（未经过 Proxy），进度永远停在 0%。修复：先用 `reactive()` 包装再放入列表。

## 7. 前端能力实现

- **SSE**：`fetch` + `ReadableStream`，按空行切分事件，兼容 `data.event`；支持 `AbortController` 中断与 `/stop` 接口。
- **TTS**：优先流式 `tts_message` 音频 → 其次 `/text-to-audio`（二进制或 base64）→ 最后浏览器 `speechSynthesis`；同一时间只允许一条消息朗读。
- **STT**：MediaRecorder 录音（webm/opus）→ `decodeAudioData` → `OfflineAudioContext` 重采样到 16 kHz 单声道 → 编码 WAV → `/audio-to-text`。原因：Dify 1.9.1 只接受 mp3/m4a/wav/amr/mpga，且 mp3 常见 MIME `audio/mpeg` 不在白名单。
- **文件上传**：读 `/parameters` 的 `file_upload`（类型、图片扩展名、15 MB、数量），XHR 上传到 `/files/upload` 显示进度，发送时以 `{type, transfer_method: local_file, upload_file_id}` 传入；`allowed_file_extensions` 只约束图片。
- **内容归属**：Dify 不提供句子级溯源。来源面板展示文档名、知识库、命中分数与片段，并明确「文档级归属，非逐句溯源」；若回答含 `[citation:N]`，渲染可点击角标并联动高亮来源卡片。

## 10. 面试可能追问的 10 个问题

1. **要点召回率怎么定义？** 组内同义词命中即算该组命中，题内命中组数/标注组数再平均；是确定性代理指标，适合回归，不适合当绝对正确率，可加 LLM-as-judge 交叉验证。
2. **来源命中率与覆盖率的区别？** 命中率是题目级「至少命中一个」，覆盖率是文档级比例；多文档题会拉低覆盖率。
3. **为什么迭代里的检索不回传来源？** Dify 对迭代/循环事件只收集不转发；移出迭代即可。
4. **重建索引 DetachedInstanceError 的原因？** 批量更新使 ORM 对象过期，之后再访问属性即脱离会话；补丁先快照 id/doc_form。
5. **为什么说中文 BM25 失效？** 关键词检索对中文返回空，hybrid 与纯向量指标基本一致。
6. **为什么关闭重排？** gte-rerank 返回空、bce 对长分块 400；多组实验收益不稳定且降低覆盖面。
7. **来源命中为什么先降后升？** v4 嵌入提升回答完整度但文档级命中下降；补干净归纳文档、办理指南并对齐标注后升到 97.7%。
8. **SSE 踩过什么坑？** 事件名在 `data.event`；必须按空行切分；Nginx 要关闭缓冲。
9. **文件上传怎么接？** `/parameters` 读取约束 → `/files/upload` 拿 id → `files` 数组引用；注意扩展名配置只约束图片。
10. **还需要 Spring Boot 后端吗？** 当前职责可被 Dify 日志替代；价值在用户体系、审计、业务集成与 API 聚合，建议保留最小后端，不建议工作流 HTTP 节点直连数据库。

## 11. 术语表

- **RAG**：检索增强生成，先检索知识库再让模型基于片段回答。
- **top_k**：检索返回的片段数量。
- **hybrid**：向量 + 关键词混合检索。
- **重排（rerank）**：对召回片段二次排序。
- **retriever_resources**：Dify 返回的引用来源数组（文档、片段、分数）。
- **SSE**：Server-Sent Events，服务端流式推送。
- **P95**：95% 请求的延迟不超过该值。

## 12. 已知限制与后续方向

- 评测是规则匹配，存在波动；可扩展 LLM-as-judge 与线上 badcase 回流。
- 来源归属只能做到文档级；句子级溯源需要模型输出结构化引用标记。
- 中文关键词检索、重排仍缺可用方案；可评估支持中文的检索后端。
- Dify 升级后需重新核对补丁；容器重建依赖 compose 挂载保证。
- 线上演示是预置数据；真实部署需要受保护的 Dify 代理。
