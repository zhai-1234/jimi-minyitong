# 简历材料 · 基米民易通（社会救助政策智能问答）

> 以下内容均来自项目真实记录（评测数据见 `evaluation/`），未夸大未做过的能力。可直接摘取 bullet 放入简历，面试追问部分用于准备口径。

## 一句话项目定位

基于 Dify 1.9.1 + 自研 Vue 3 前端的 RAG 社会救助政策问答智能体，用 50 题六类场景评测体系驱动检索、提示词与知识库迭代，最终实现要点召回 95.3%、来源命中 97.7%、超纲拒答 100%。

## 技术栈

Dify 1.9.1（工作流 / 知识库 / 插件）· RAG（hybrid 检索、top_k、重排评估）· Vue 3 + Vite + Pinia + Element Plus · SSE 流式 · Python 标准库评测脚本 · Spring Boot 3.5 + MyBatis + MySQL（可选日志服务）· Docker Compose · PowerShell/Windows 本地环境

## 量化 bullet（5 条）

- **搭建 50 题六类场景（单政策/多政策/口语化/粤语/超纲/边界）RAG 评测体系**，仅依赖 Python 标准库，支持 mock/真实双模式与报告对比；最终版本关键要点召回 **95.3%**、来源命中 **97.7%**、拒答正确率 **100%**，平均延迟 **6.6 s**、P95 **8.4 s**。
- **定位并修复 Dify 引用来源丢失的两层根因**（迭代子图内事件不向上转发、LLM 上下文接的是字符串而非检索结果数组），来源指标从不可用恢复为 **72.1%**，再通过标注修正、原始问题检索替代融合查询、补充归纳文档与办理指南，把来源命中率从 **72.1% 提升到 97.7%**（+25.6 pt）。
- **延迟优化 -30.2%**：重写「问题分析」提示词（max_tokens=80、temperature=0.1）、回答限制 350 字、修复只按英文逗号切分导致中文子问题退化的问题；平均延迟 **8813 ms → 6153 ms**，P95 **16184 ms → 9351 ms**，答案长度 **932 → 376 字**（-59.6%）。
- **知识库与检索治理**：把惠民清单中的医疗/教育/住房/就业/残疾人救助整理成归纳文档、补齐办理指南与镇街联系方式；累计开展 **8 组以上**嵌入模型/重排/top_k 对照实验（含 17 题平衡子集 A/B 与全量 50 题矩阵），最终选择 v1 嵌入 + 归纳文档 + 办理指南配置。
- **自研 Vue 3 对话前端直连 Dify Service API**：SSE 增量渲染与中断、会话管理、来源面板、点赞点踩、回答朗读（流式 TTS / text-to-audio / 浏览器合成三级回退）、浏览器录音转 16 kHz WAV 的语音输入、按应用参数校验的文件上传；配套可选的 Spring Boot 问答日志服务（6 个单测通过）。

## 面试可能追问的 10 个问题与回答要点

1. **要点召回率是怎么定义的？**
   测试集每题标注若干「要点组」，组内任一同义词命中即算该组命中；题内命中组数 / 标注组数，再对题目取平均。它是确定性代理指标，不理解语义，适合做回归对比，不宜当绝对正确率；可扩展 LLM-as-judge 交叉验证。

2. **来源命中率和来源覆盖率有什么区别？**
   命中率是「至少命中一个应引用文档的题目占比」，偏高；覆盖率是「命中应引用文档数 / 标注文档数再取平均」，多文档题会拉低。接口不回传引用时两者都不可用，此时用「答案文本中出现文档名」的代理指标。

3. **为什么 Dify 迭代节点里的知识检索不回传来源？**
   Dify `EventManager.dispatch()` 对迭代/循环内的事件只收集不转发（源码注释 “Events in loops or iterations are always collected”），`retriever_resources` 到不了 API。解决方式是把检索移出迭代，改为查询拆解 → 单次融合检索 → 生成；若要多查询并行，需要拆成固定数量的静态并行分支。

4. **重建知识库索引时遇到的 DetachedInstanceError 是什么？**
   `deal_dataset_vector_index_task` 清理索引后访问已脱离 SQLAlchemy 会话的文档对象。补丁做法是先取出文档 id/doc_form 再清理；补丁仅存在 api/worker 容器内，容器重建会丢失，原文件备份在 `evaluation/diagnostics/`。

5. **为什么说 hybrid 检索里的 BM25 对中文失效？**
   知识库关键词检索对中文查询返回空结果，实际只有向量检索在贡献召回。实验中用「纯向量」对比「hybrid」指标基本一致，印证了这一点。后续可换支持中文分词的检索后端或引入语义重排。

6. **为什么关闭了重排？**
   配置的 tongyi `gte-rerank`（及 v2）直接调用返回 0 条，wenxin `bce-reranker-base` 对知识库长分块返回 400；为保证主链路可用先关闭重排，并做过多组「重排取 TopN / 文档名优先」实验，收益不稳定且牺牲覆盖面，最终未启用。

7. **来源命中率为什么从 90.7% 又掉到 76.7%，最后怎么回到 97.7%？**
   切到 v4 嵌入后回答更完整但文档级命中下降；根因是惠民清单解析噪声大、18.7 万字的手册挤占 top_k。通过补充干净归纳文档、办理指南、停用无效的就业文档，并把标注对齐到真实文档，最后到 97.7%。

8. **SSE 流式解析踩过什么坑？**
   Dify 新版把事件名放在 `data.event` 而不是 `event:` 行，旧解析导致 `message_end` 永远识别不到、来源面板为空；同时流式输出必须按空行切分事件，Nginx 需关闭 `proxy_buffering`。

9. **文件上传是怎么接的？**
   读 `/v1/parameters` 的 `file_upload`（允许类型、扩展名、数量、15MB 限制），先传 `/v1/files/upload` 拿 `upload_file_id`，再在 `/chat-messages` 的 `files` 数组里用 `{type, transfer_method: local_file, upload_file_id}` 引用；注意 `allowed_file_extensions` 在 Dify 中只约束图片。

10. **这个项目还需要 Spring Boot 后端吗？**
    当前后端只做问答日志落库/查询，Dify 自带日志基本可替代；它的价值在于用户体系、权限、审计、历史会话分析和对外 API 聚合。建议保留一个「最小后端」（日志/鉴权/聚合），不要用工作流 HTTP 节点直连业务库。详见 `docs/架构决策-是否需要后端.md`。
